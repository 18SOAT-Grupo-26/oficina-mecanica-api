# Modelo C4: Oficina Mecânica API

Visão da arquitetura da fase 1 em três níveis do [modelo C4](https://c4model.com/): contexto, contêineres e
componentes da API. Os diagramas são do jeito que o sistema sobe pelo `docker-compose.yml` e do jeito que o código está
organizado. As decisões estão nas ADRs:
[001 (monólito em camadas)](../adr/0001-monolito-em-camadas.md),
[002 (banco de dados)](../adr/0002-escolha-do-banco-de-dados.md),
[003 (transações)](../adr/0003-estrategia-de-transacoes.md),
[004 (segurança)](../adr/0004-seguranca.md) e
[005 (testes)](../adr/0005-estrategia-de-testes.md).

Legenda das cores, em todos os níveis:

| Cor           | Elemento                                  |
|---------------|-------------------------------------------|
| Azul-escuro   | Pessoa (perfil de usuário)                |
| Azul          | O sistema ou um contêiner dele            |
| Azul-claro    | Componente dentro da API                  |
| Cinza         | Fora do sistema ou fora do escopo da fase |

## Nível 1: contexto

Quem usa o sistema e para quê. Na fase 1 não há front-end: os três perfis chamam a API REST pelo Postman ou pelo Swagger
UI, autenticados com JWT. Não há integração com sistemas externos em tempo de execução.

```mermaid
flowchart TB
    admin["<b>Administrador</b><br/>[Pessoa, perfil ADMIN]<br/><br/>Cadastra usuários e o catálogo,<br/>exclui cadastros e cancela OS"]
    funcionario["<b>Funcionário</b><br/>[Pessoa, perfil FUNCIONARIO]<br/><br/>Atende o cliente: cadastra cliente<br/>e veículo, abre a OS, gera o orçamento,<br/>registra a decisão e atualiza o status"]
    cliente["<b>Cliente</b><br/>[Pessoa, perfil CLIENTE]<br/><br/>Acompanha o status das próprias OS"]
    operacao["<b>Equipe técnica</b><br/>[Pessoa]<br/><br/>Acompanha a saúde da API<br/>e os indicadores da oficina"]

    sistema["<b>Oficina Mecânica API</b><br/>[Sistema de software]<br/><br/>Gestão de clientes, veículos, serviços,<br/>peças e estoque e o ciclo de vida<br/>da Ordem de Serviço"]

    notificacao["<b>Notificação do cliente</b><br/>[Sistema externo, fase 2]<br/><br/>E-mail ou mensagem com o orçamento<br/>e a mudança de status"]

    admin -- "Administra<br/>[HTTPS/JSON, JWT]" --> sistema
    funcionario -- "Opera as OS<br/>[HTTPS/JSON, JWT]" --> sistema
    cliente -- "Consulta as próprias OS<br/>[HTTPS/JSON, JWT]" --> sistema
    operacao -- "Monitora<br/>[painéis e alertas]" --> sistema
    sistema -. "Avisaria o cliente<br/>[fora do escopo]" .-> notificacao

    classDef pessoa fill:#08427b,stroke:#052e56,color:#ffffff
    classDef sistema fill:#1168bd,stroke:#0b4884,color:#ffffff
    classDef externo fill:#8a8a8a,stroke:#6b6b6b,color:#ffffff,stroke-dasharray:5 5
    class admin,funcionario,cliente,operacao pessoa
    class sistema sistema
    class notificacao externo
```

- **Permissões de cada perfil:** a matriz completa está na ADR 004, seção 4. O cliente só enxerga as próprias OS, e o
  `clienteId` vem do token, nunca da URL.
- **Aprovação do orçamento:** nesta fase, o cliente decide fora do sistema e o funcionário registra a decisão. A
  aprovação direta pelo cliente e a notificação ficam para a fase 2.
- **Ferramentas de desenvolvimento** (GitHub Actions, SonarCloud, Gitleaks e o SonarQube local) não fazem parte do
  sistema em execução e ficam fora do diagrama.

## Nível 2: contêineres

O que roda no `docker compose up`. A API é um monólito único (ADR 001) e é o único contêiner que os usuários chamam.

```mermaid
flowchart TB
    usuarios["<b>Administrador, Funcionário e Cliente</b><br/>[Pessoas]<br/><br/>Usam o Postman ou o Swagger UI"]
    operacao["<b>Equipe técnica</b><br/>[Pessoa]"]

    subgraph sistema ["Oficina Mecânica API [docker compose]"]
        direction TB
        api["<b>API</b><br/>[Contêiner: Java 25, Spring Boot 4.1.2]<br/><br/>Regras de negócio, autenticação JWT,<br/>autorização por perfil, Swagger UI.<br/>Aplica as migrations do Flyway na subida<br/><br/>porta 8081, /api/v1"]
        db[("<b>Banco de dados</b><br/>[Contêiner: PostgreSQL 18]<br/><br/>Cadastros, estoque, OS, itens,<br/>histórico de status e usuários.<br/>Volume pgdata<br/><br/>porta 5432")]
        prometheus["<b>Prometheus</b><br/>[Contêiner: Prometheus 3.15]<br/><br/>Coleta as métricas a cada 15 s,<br/>calcula os sinais de ouro<br/>e avalia os alertas<br/><br/>porta 9090"]
        grafana["<b>Grafana</b><br/>[Contêiner: Grafana 13.2]<br/><br/>Painel provisionado com os<br/>sinais de ouro e as métricas da OS<br/><br/>porta 3000"]
    end

    usuarios -- "Chama a API REST<br/>[HTTP/JSON, Bearer JWT]" --> api
    api -- "Lê e grava<br/>[JDBC, HikariCP]" --> db
    prometheus -- "Coleta /actuator/prometheus<br/>[HTTP]" --> api
    grafana -- "Consulta<br/>[PromQL]" --> prometheus
    operacao -- "Vê painéis e alertas<br/>[HTTP]" --> grafana

    classDef pessoa fill:#08427b,stroke:#052e56,color:#ffffff
    classDef conteiner fill:#438dd5,stroke:#2e6295,color:#ffffff
    class usuarios,operacao pessoa
    class api,db,prometheus,grafana conteiner
```

| Contêiner    | Imagem (compose)                 | Responsabilidade                                                                                     |
|--------------|----------------------------------|------------------------------------------------------------------------------------------------------|
| `api`        | build do `Dockerfile`            | Toda a regra de negócio. Sobe só depois do `db` saudável e expõe só `health` e `prometheus` no Actuator |
| `db`         | `postgres:18-alpine`             | Única fonte de dados. O esquema é das migrations V1–V10 do Flyway, com `ddl-auto: validate` (ADR 002) |
| `prometheus` | `prom/prometheus:v3.15.1`        | Regras dos sinais de ouro (`regras-sinais-ouro.yaml`) e alertas (`alertas.yaml`)                     |
| `grafana`    | `grafana/grafana:13.2.4`         | Fonte de dados e painel provisionados em `grafana/provisioning/`                                     |

- O `sonarqube` também está no `docker-compose.yml`, mas é ferramenta de desenvolvimento (análise local antes do PR) e
  não participa do sistema em execução.
- O Prometheus também tem um alvo para a API rodando fora do Docker (`host.docker.internal:8081`), para quem roda a API
  pela IDE.

## Nível 3: componentes da API

Como o contêiner `api` é organizado por dentro: monólito em camadas, no estilo ports & adapters (ADR 001). As setas
seguem a regra de dependência: o `core` não conhece o `controller` nem a `infrastructure`.

```mermaid
flowchart LR
    usuarios["<b>Usuários</b><br/>[Postman ou Swagger UI]"]
    db[("<b>PostgreSQL 18</b><br/>[Contêiner]")]
    prometheus["<b>Prometheus</b><br/>[Contêiner]"]

    subgraph api ["API [contêiner Spring Boot]"]
        direction LR

        subgraph entrada ["Adapters de entrada"]
            direction TB
            seguranca["<b>Segurança</b><br/>[infrastructure/config/security]<br/><br/>SecurityConfig, JwtAuthenticationFilter,<br/>SegredoJwtConfig, RotasPublicas"]
            controllers["<b>Controllers REST</b><br/>[controller/admin, auth, cliente]<br/><br/>*Controller implementa *API<br/>(rotas e OpenAPI), @PreAuthorize"]
            handler["<b>Tratamento de erros</b><br/>[shared/handler]<br/><br/>HandlerException devolve<br/>ErrorTemplate, sem stack trace"]
        end

        subgraph core ["core"]
            direction TB
            portin["<b>Ports de entrada</b><br/>[core/port/in]<br/><br/>*UseCasePortIn e os DTOs<br/>*Request e *Response"]
            usecases["<b>Casos de uso</b><br/>[core/usecase]<br/><br/>Um por contexto, @Transactional.<br/>Orquestram cadastros, estoque e métricas"]
            dominio["<b>Domínio</b><br/>[core/domain]<br/><br/>Agregado OrdemServico, StatusOrdemServico,<br/>Cliente, Veiculo, PecaInsumo, Servico,<br/>Usuario e objetos de valor<br/>(Documento, Placa, ValorMonetario)"]
            portout["<b>Ports de saída</b><br/>[core/port/out]<br/><br/>*PortOut com modelos de domínio"]
        end

        subgraph saida ["Adapters de saída e configuração"]
            direction TB
            persistencia["<b>Persistência</b><br/>[infrastructure/persistence]<br/><br/>*PersistenceAdapter, *Entity (JPA),<br/>*JpaRepository, *PersistenceMapper"]
            metricas["<b>Métricas e documentação</b><br/>[infrastructure/config/metrics, docs]<br/><br/>Micrometer, Actuator, OpenApiConfig"]
            flyway["<b>Migrations</b><br/>[resources/db/migration]<br/><br/>Flyway V1–V10, na subida"]
        end
    end

    usuarios -- "HTTP/JSON, Bearer JWT" --> seguranca
    seguranca -- "Autentica e repassa" --> controllers
    controllers -- "Chama" --> portin
    controllers -. "Exceções" .-> handler
    usecases -. "Implementa" .-> portin
    usecases -- "Aplica as regras" --> dominio
    usecases -- "Chama" --> portout
    persistencia -. "Implementa" .-> portout
    persistencia -- "SQL via JPA e<br/>UPDATE condicional de estoque" --> db
    flyway -- "Cria e evolui o esquema" --> db
    prometheus -- "Coleta /actuator/prometheus" --> metricas

    classDef componente fill:#85bbf0,stroke:#5d82a8,color:#000000
    classDef conteiner fill:#438dd5,stroke:#2e6295,color:#ffffff
    classDef pessoa fill:#08427b,stroke:#052e56,color:#ffffff
    class seguranca,controllers,handler,portin,usecases,dominio,portout,persistencia,metricas,flyway componente
    class db,prometheus conteiner
    class usuarios pessoa
```

| Componente           | Pacote                                    | Pode depender de                                       |
|----------------------|-------------------------------------------|--------------------------------------------------------|
| Controllers REST     | `controller/<admin\|auth\|cliente>`       | `core/port/in`, `shared`                               |
| Ports de entrada     | `core/port/in/<contexto>`                 | `core/domain`                                          |
| Casos de uso         | `core/usecase/<contexto>`                 | `core/domain`, `core/port`, `shared`                   |
| Domínio              | `core/domain/<contexto>`                  | `shared/exception` e utilitários puros de `shared/utils` |
| Ports de saída       | `core/port/out/<contexto>`                | `core/domain`                                          |
| Persistência         | `infrastructure/persistence/<contexto>`   | `core/domain`, `core/port`, `shared`                   |
| Segurança            | `infrastructure/config/security`          | `core/port/in` (o filtro usa o `JwtTokenUseCasePortIn`) |
| Tratamento de erros  | `shared/handler`                          | `shared/exception`                                     |

Os contextos são os mesmos em todas as camadas: `auth`, `usuario`, `cliente`, `veiculo`, `servico`, `pecainsumo` e
`ordemservico`. O fluxo da OS passando por esses componentes, passo a passo, está nos
[diagramas de sequência](sequencia-ordem-servico.md).
